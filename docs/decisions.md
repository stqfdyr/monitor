# 设计决策

**动手改之前读这个。** 要推翻其中任何一条，先跟用户确认。

标注：**[用户]** = 用户拍板；**[默认]** = 按项目原则定的，用户确认过或未反对。

---

## 通信

### WebSocket + JSON-RPC 2.0 **[用户]**

这类探针里最常见、最经得起考验的一套。一条长连接双向都能主动发，报文自带方法名，`curl` 和
浏览器控制台就能读。

**否决**：HTTP POST 轮询——hub 无法主动下发探测任务；gRPC / protobuf——多一个 codegen 步骤和
`protoc` 依赖，JSON 在这个数据量下够用且调试方便。

只用**通知**（无 `id`、无响应）而不是完整 RPC：没有任何一个调用需要返回值。

### token 走 `Authorization` 头，不走 URL query **[默认]**

`?token=xxx` 是更省事的写法，但 query string 会进 nginx/caddy 的 access log。agent 不是浏览器，能设请求头，所以没有理由把 token 放 URL 里。

改动位置：[agent 仓库](https://github.com/stqfdyr/agent) 的 `src/main.rs` 的 `session()`，`src/agent_ws.rs` 的 `bearer()`。

## Agent

### 只支持 Linux **[用户]**

连锁效果很大：直接读 `/proc` 和 `statvfs`，不引入 `sysinfo`。数据更准（`sysinfo` 的内存和硬盘
口径是错的，见 agent 仓库的 data-accuracy.md）、二进制更小、零抽象层。

**加跨平台等于推翻整个 `collect.rs`。** 先问用户。

### agent 完全无状态 **[默认]**

agent 不写任何文件、不记忆任何跨重启的状态。它只上报「此刻内核告诉我的数字」，累加全部由 hub 负责。

**为什么**：agent 跑在别人的 VPS 上，可能被重装、被迁移、被 kill -9。让它维护持久状态就等于给每台机器引入一个可能损坏的状态文件。hub 只有一个，备份和修复都容易。

**否决**：agent 侧落盘记流量——每台 VPS 一个状态文件，重装即丢。

### 不做自动更新 **[用户]**

自更新意味着 agent 能以 root 下载并执行任意二进制，是整个探针最大的攻击面。升级方式是重跑一遍
安装命令，一行的事。

## Hub

### 零配置文件 **[默认]**

只有四个命令行参数：`--listen`、`--db`、`--themes`、`--site`。`--themes` 默认是数据库旁的 `themes/`；其余全部存在 SQLite 的 `setting` 表里，在面板配置。

**为什么**：少一个 TOML 解析、少一类「配置文件在哪/权限对不对/和 DB 不同步」的问题。密钥存在 DB 里也比存在明文配置文件里好。

首次启动生成一次性应急密码打印到 stdout——否则全新的 hub 在 GitHub 配好之前完全进不去。

**`--site` 是可选的**，缺省不推导任何地址——见下一节。

### 默认就是 ip + port，`--site` 只为反代而留 **[用户]**

不带参数启动就监听 `0.0.0.0:28080`，浏览器直接开 `http://<IP>:28080` 即可，不需要域名、证书，也不
需要填任何地址。仿 komari 的部署体验。

改造前 `--site` 缺省会被推导成 `http://0.0.0.0:8080`——一个谁都打不开的地址，还会被写进安装命令。
现在缺省是**空**，三处要地址的地方各有各的答案：

| 要地址的地方 | 有 `--site` | 没有 `--site` |
|---|---|---|
| 安装命令、OAuth 回调 | 用它 | 面板回落 `location.origin`，即浏览器地址栏里的地址 |
| cookie 的 `Secure` | 看它的 scheme | 看请求的 `X-Forwarded-Proto`，多级代理取第一跳 |
| 启动打印的地址、明文告警 | 用它 | 监听地址，`0.0.0.0` 换成本机出网 IP |

`X-Forwarded-Proto` 是客户端可伪造的头，**只有这个标志信它**：伪造 `https` 的代价是自己的浏览器存
不下 session，伪造 `http` 是把 `Secure` 从自己已有的 cookie 上摘掉，两头都碰不到别人的会话。

`main::outbound_ip()` 问内核「去 1.1.1.1 该走哪个本机地址」，不发包、断网也能答。NAT 后面拿到的是
内网地址——hub 不可能知道自己的公网地址，所以一键脚本用查到的公网地址覆盖它。

**反代场景通常不用填 `--site`**：面板拼命令用的是 `me.site || location.origin`，所以从
`https://hub.example.com` 进后台，命令自己就是那个地址，cookie 的 `Secure` 也由 `X-Forwarded-Proto`
兜住。只有两种情况要填：进后台的地址不是节点能用的地址（监听回环再走 SSH 隧道，地址栏是
`127.0.0.1`），或者反代不发 `X-Forwarded-Proto`。

### 一键脚本只监听回环 **[用户]**

`install-hub.sh` 写死 `--listen 127.0.0.1:$PORT`，而**二进制自己的默认值仍是通配符**——两者服务的
是不同场景：手工跑和 Docker 都需要能从外面连上（容器里绑回环，`-p` 就映射不到），而一键脚本装出来的
是长期在线的服务，那里默认值该偏安全。

代价是装完不能立刻打开面板，必须先配反代。所以脚本最后不是一句「记得配 TLS」的告警，而是把
nginx、caddy、cloudflared 三种配法直接打出来，并说明「面板只监听本机是故意的」——**装到一半的
观感是这个改动最大的成本**，提示写不好就是纯粹的劝退。

`--site` 依然不用填：面板拼命令用 `location.origin`，域名一通就全对了。

顺带修掉的：重跑升级会把 unit 重写成默认值，**端口和 `--site` 都会丢**，而反代正指着旧端口。现在
没显式给的参数从旧 `ExecStart` 里读回来。

**否决**：留一个 `--expose` 之类的开关放行 ip:port（和这次收紧的目的直接冲突，真需要的人可以自己
跑二进制）；在菜单里问监听地址（多一个大多数人答不上来的问题）。

### 默认监听双栈通配符 **[用户]**

`--listen` 默认 `[::]:28080`，不是惯例的 `0.0.0.0`。Linux 的 `bindv6only` 默认为 `0`，一个 v6
socket 通过 v4-mapped 地址同时收两族，所以双栈机器什么都不用配。启动时读
`/proc/sys/net/ipv6/bindv6only`：读不到（内核 `ipv6.disable=1`，那个目录整个不存在）或值为 `1`
（那样它只收 v6，会把所有 v4 节点挡在外面）就退回 `0.0.0.0:28080`；万一 bind 仍然失败，**只在没给
`--listen` 时**再退一次到 v4——写了地址的人是认真的，那种情况必须报错而不是换一个。

**为什么不跟惯例**：节点是主动连 hub 的，hub 监听哪一族就决定了谁连得上，而两边都是静默失败——
只有 IPv6 的节点对一个 v4 地址根本没有路由，它只会一直重连，两头都不会有任何一行说明原因。komari
在这件事上是 `0.0.0.0:25774` 写死（一键脚本还把它焊进 unit），全仓库没有一处 `[::]`、`bindv6only`
或双 socket，文档也没提。

`install-hub.sh` 后来改成只监听回环，不再走这条规则——见上面那一节。这里说的是二进制自己的默认值，
手工部署和 Docker 用的就是它。

**否决**：默认端口留 8080（撞 nginx 和各种面板的概率太高，komari 用 25774 是同一个理由）；后端从
`Host` 头推导对外地址（多一个服务端信任点，而浏览器本来就知道自己的 origin，不必让服务端告诉它）。

### hub 只有 IPv4 时不改架构 **[用户]**

问过一轮「纯 v4 的 hub 让 v6-only 节点没意义，转发架构是不是要重设计」。不改，因为**转发不是那道
坎**：agent 的价值全在那条常驻 WebSocket 上，节点连不上 hub 就等于没接入，二进制从哪下载都一样。

而在这个前提下，转发恰好是**唯一**能让 v6-only 节点装上的路。实测（2026-09，纯 v6 无 NAT64 的
alice）：

| 路径 | 结果 |
|---|---|
| alice → `github.com/.../releases/...` | `000`——github.com 只有 A 记录，无路由 |
| alice → `<hub>/agent/x86_64` | `200`，1 815 264 字节，走 `2606:4700:3037::ac43:9335` |

`objects.githubusercontent.com`、`release-assets.githubusercontent.com`、`codeload.github.com`
同样没有 AAAA（只有 `raw.githubusercontent.com` 有）。所以「改成节点直连 GitHub」不是修复，是把
现在能用的这批机器也一起弄坏。komari 两处都直连 GitHub，退路是一串加速镜像和 `--install-ghproxy`，
即把问题推给用户。

真正的约束是路由，不是架构：**节点必须能到达 hub**。给 v4-only 的 hub 加一个 v6 入口有三条路，都
不需要改代码——机器申请一个 v6 地址（多数 VPS 免费给 /64）、套 Cloudflare 之类的双栈 CDN、或用
Cloudflare Tunnel（出站建隧道，源站纯 v4 也能有双栈边缘，本项目自己在用的就是这条）。

**否决**：节点侧内置 NAT64/DNS64 兜底（`64:ff9b::` 得有人提供，agent 变不出来）、hub 之间做中继
（为一个路由问题引入一整套拓扑）。

### 明文 hub 用 `--insecure` 显式放行 **[用户]**

agent 和 `install.sh` 都拒绝明文连远程 hub：token 会明文传输，而且装 agent 时下载的二进制走同一条
未经验证的通道，那个二进制马上要以 root 跑起来。裸 ip:port 部署恰好就是明文，所以这道闸得留个开关。

做成显式开关，而不是直接放开：

- `install.sh --insecure` 跳过拒绝，往 stderr 打三行风险说明，并把 `--insecure` 写进 agent 的 `ExecStart`
- agent 的 `--insecure` 除了放行，还让**裸主机名不再升级成 TLS**——否则这个 flag 会去 dial 一个永远
  握不上手的 `wss://`
- 面板检测到 hub 是明文远程（`needsInsecure()`）就自动把 `--insecure` 拼进命令，并在弹窗里红字说明

komari 对此零检查：`-e http://1.2.3.4:25774` 直接就用，明文传 token 没有任何提示。

**否决**：默认放开（安全降级必须可见）、自签证书或内置 ACME（项目明确不做）。

### hub 一键脚本 `install-hub.sh` **[用户]**

有终端时给菜单（安装 / 升级、卸载、状态、日志），`curl | sh` 没有终端可读答案就按默认装——komari
那份脚本在管道里菜单会乱。

和 komari 的 `install-komari.sh` 逐项对比：

| | komari | 这里 |
|---|---|---|
| 下载校验 | 无 | 核对 release 的 `sha256sums.txt` 才落盘 |
| 服务身份 | `User=root` | `DynamicUser=yes` + `StateDirectory=` |
| 单元加固 | 无 | `ProtectSystem=strict` 那一套，与 agent 一致 |
| curl 超时 | 无 | 全部带 `--max-time` |
| 缺依赖 | `apt update` 全量升级 | 只报错，不动别人的系统 |
| 已有部署 | 直接覆盖 | 单元带 `# managed-by:` 标记，认不出就拒绝动 |
| 公网地址 | `hostname -I`，NAT 下是内网地址 | 先查公网地址，失败才回落 `hostname -I` |
| TUI | 依赖 whiptail / dialog | 纯 ANSI，非 tty 自动去色 |
| 版本查询 | 解析 GitHub API 的 JSON | 读下载重定向里的 tag，不受 API 限流 |

`managed-by` 那条是实测踩出来的：开发机上正跑着一个手工部署的 hub（`--listen 127.0.0.1:25775`、
`--site https://...`），脚本原本会把它的单元换成 `0.0.0.0:28080` 且无 TLS，`--purge` 还会删掉它的库。

数据固定在 `/var/lib/monitor`，不提供 `--data`：`StateDirectory=` 已经把创建和归属都办了。
`DynamicUser=` 下真实目录是 `/var/lib/private/monitor`，`/var/lib/monitor` 是 systemd 留的符号链接，
所以 `--purge` 要删两个路径。

**否决**：菜单里问 `--site`（大多数人不需要，问了反而像必填）、`--data` 自定义数据目录、发布通道选择
（只有 tag release，没有 snapshot）、装指定版本（要装旧版的人会自己 curl）。

### 后台与默认主题嵌进二进制 **[默认]**

`rust-embed` 把 `web-admin/dist` 和下载解出来的 `target/theme/dist` 打进 hub。没有安装第三方主题时，部署仍是一个二进制 + 一个 db 文件。

注意：**debug 构建时 rust-embed 从磁盘读**，所以开发时要保留两个 `dist/`；release 才真正嵌入。

### 单管理员，不做用户表 **[默认]**

没有 `user` 表，没有角色，没有权限系统。要么是管理员（有有效 session），要么不是。

**为什么**：自用探针。加多用户就要加权限模型、加「谁能看哪些节点」，是另一个量级的复杂度。

### 历史明细每分钟一行，不做降采样 **[默认]**

agent 每 2 秒上报（实时视图用），但 `metric` 表每节点每分钟只写一行（`src/agent_ws.rs` 里 `now / 60` 变了才写）。超过保留天数直接删，不做多级降采样。

**为什么能这么简单**：因为累计流量不是从 `metric` 算出来的，所以明细可以随便删。见 [traffic.md](traffic.md)。

### 历史行里的网速是这一分钟的平均值，不是某一秒的读数 **[默认]**

**这条推翻了之前的设计。** 原来 `metric.net_rx/net_tx` 直接存 agent 报上来的瞬时速率，也就是
跨分钟那一次上报所测的那一秒——**一分钟里的 1/60 采样**。窗口越宽降采样越狠：7 天视图一个点代表
840 秒，采样率跟着掉到 1/840。

实测（cc，30 秒内下载 53.0 MiB，起止都落在两次采样之间）：累计器记到 53.0 MiB，历史图上 0.04 MiB
——一条完全没发生过的平线，同一件事两个通路差三个数量级。

根因是 hub 每次上报都在 `db::accumulate()` 里算出了精确增量，却往历史表里存 agent 的估计值。
现在 `Agent.mark` 记住上一行的 `(时刻, total_rx, total_tx)`，跨分钟时用两行之间的累计差除以实际
秒数，**图的积分因此等于累计器**。同样的实验：53.41 MiB，误差 0.8%。

实时视图不变，仍然是 agent 的瞬时速率——「当前网速」要的就是那个。

同一行上的其它字段也一样：`cpu`、`mem_used`、`swap_used`、`disk_used`、`tcp`、`udp`、`procs`
现在都是**分钟内均值**（`Agent.minute`），不是边界那一秒的读数。整数列按整数写回去——
`insert_metric` 用 `as_i64` 读它们，一个带小数的值会被读成 0。

**`load1` 故意不平均**：内核给的本来就是过去一分钟的均值，再平均一次等于摊到两分钟。

**均值不是极值。** 5 秒钟 100% 的 CPU 尖峰，均值是 8%——比原来的 0% 诚实，但仍然不显眼。
想看尖峰要单独存一列 `cpu_max`，那是一次 schema 变更加一个图表决定，需要时再提。

### 图表窗口的降采样取桶内均值，不取桶内一行 **[默认]**

**这条和上面那条是同一个 bug 的两层。** 写入侧已经把行改成分钟内均值了，读取侧
（`db::metrics` / `db::ping_records`）又把它扔掉一次：原来是 `SELECT MAX(ts), cpu, ... GROUP BY ts/step`，
`MAX(ts)` 配裸列是 SQLite 的「取最大值那一行」，也就是**一桶十四分钟只留一分钟，还是随机的那一分钟**。

实测 cc 的 7 天网络图（step=840s）：

| | 7 天窗口积分出来的流量 |
|---|---|
| 全量分钟行 | 27.52 GB |
| 取桶内一行（原来） | **53.69 GB** |
| 取桶内均值（现在） | 28.02 GB |

**图的积分又一次不等于累计器**，而且高了 95%。改成 `AVG(...)` 之后误差只剩最后半桶的边界。
1 小时和 6 小时窗口 step 正好是 60 秒，一桶一行，均值等于原值——只有 24 小时和更宽的窗口变。

时间戳同时从「桶里某一行的 ts」改成 `(MIN(ts)/step)*step`，也就是**桶自己的起点**。
副作用是所有序列落在同一张网格上：4 个探测的一天，前端要画的行数从 2 868 掉到 717。
代价是窗口开头那一桶的时间戳可能早于 `since`，最多一个 step——Grafana / Prometheus 也是这么标的。

### 探测超时进图，不被过滤掉 **[默认]**

TCP 探测超时在库里是 `latency = -1`。前端原来 `filter(p => p.latency >= 0)` 把它们全扔了，
recharts 的 `connectNulls` 再把断点连起来——一条丢 54% 包的探测在图上是一条正常的线；整段没通的
探测（89 次全超时）则整条消失。降采样那一层还先掩盖了一半：一天 788 次超时，取桶内末值之后只剩
389 次，再被过滤成 0 次。

现在 `ping_records` 分开算：`latency` 是桶内**答上来的那些**的中位数，全超时就是 `null`；
`loss` 是这桶超时的百分比，为 0 时整个字段不发（一天 2 880 行，每行一个 `"loss":0` 是 29 kB）。
前端把百分比写在图例上，tooltip 写这一桶的。

**没做的**：按时间画丢包（Smokeping 靠线的颜色，Uptime Kuma 靠图下一条心跳条）。四条探测已经压在
同一张图上，再叠一层就是再加一层噪音。要看丢包发生在什么时候，得先决定这张图继续叠还是拆成
一探测一图——那是一次图表决定，问过再做。

### 延迟线画中位数，带画桶内极差 **[用户]**

**桶内被均值抹掉的抖动，比线画出来的趋势还大。** 实测 cc 24 小时窗口：

| | p50 | p90 | p99 |
|---|---|---|---|
| 桶内极差（max−min） | 11ms | **63ms** | 113ms |
| 相邻桶之间的跳动 | 8ms | 25ms | — |

一个桶里两次 ping 是 200 和 263，画成 231 的一个平点——链路在抖 63ms 这件事完全没了，
而线本身的正常起伏只有 8ms。这就是 Smokeping 三十年来在中位数周围画灰色「smoke」的理由。

**线用中位数不用均值**：一次 SYN 重传是几十毫秒，能把均值拖走，中位数不会——错的是那个读数，不是链路。
SQLite 没有 `median()`，怎么算见下面「桶在 Rust 里折，不在 SQL 里排」。

**带只在只剩一条探测时画**。四条一起画，带互相叠成雾，而且极值会把 Y 轴从 165–385 拉到
140–420，把线本身压扁。概览看线，收窄到一条才给抖动。

**带不参与削峰**：削峰是为了把重传从线上拿掉，连带从带上拿掉就等于藏起带存在的理由。

### 延迟图的高度量出来，不写常数 **[默认]**

原来是 `h-[calc(100svh-26rem)]`。26rem 是上方内容在**桌面上**的高度；手机上信息栏是单列六行、
高出一半，于是图跑到屏幕外，带丢包率的图例整个看不见。

现在量 `getBoundingClientRect().top`，列高设成剩下的视口，图表 `flex-1 min-h-0` 吃剩余、图例占
自己那点。图例高度同样不能是常数——四条探测在桌面是一行 chip、在手机折成两行。实测 390/768/1280
三个宽度，图例都在首屏内。

### 分辨率由屏幕决定，聚合是退让不是默认 **[用户]**

**这条推翻了「探测的桶固定 5 分钟」。** 那一版的理由是「桶里要有够多样本，中位数才有中间、带才有
两端」，做出来是 24 小时只有 288 个点，而库里有 1440 行。

不只是观感问题：**一张 288 个点的图读起来就是「采了 288 次」，不管底下的采集器实际跑多密；
在探测图上，这是一句关于网络的断言。** 所以：

- 请求带上屏幕能分辨的点数（`innerWidth × devicePixelRatio`，设备像素而不是 CSS 像素——线最终画在设备像素上）
- hub 只在样本多于像素时才抽稀，`SAMPLES` 上限提到 1440（一天的分钟数）
- 于是 1/6/24 小时都是全量，7 天才发生聚合

代价由「按 tab 只取一半」付掉：每个 tab 只画一半数据却下载两份，不画的那半占每次响应的 37–62%。

这条契约反复过四版（720 写死 → 跟视口 → 探测预算 250 → 固定 5 分钟桶 → 现在），根因是一直没写下
「分辨率该由什么决定」，每次都在局部修症状。写下来就不再动：**分辨率由屏幕决定。**

### 历史里的负载和 swap 不画也不发 **[用户]**

负载原来就在 CPU 面板里，但和 CPU% 共用一根标着 `%` 的轴——0.34 画在 0.34% 处，等于不存在。
我给它加了独立右轴，把一条看不见的线变成了显眼的一条。用户的回应是「只显示 cpu 就行了，你擅自加了负载」。
**整条去掉，不是退回看不见。** 面板标题从「CPU 与负载」变成「CPU」。

实时负载不受影响——它在节点卡片上，来自 socket 推的快照，不走这个接口。

`load1` 和 `swap_used` 于是都成了没人画的字段，从响应里一起下线。列还留着（那是机器当时状态的记录，
删列是一次迁移），但线上不再传。

### 探测线用颜色区分 **[废案 · 做完了，用户决定先不启用]**

灰阶配色下四条探测靠 `strokeDasharray` 区分。**这在桶宽几分钟时管用，在每一次 ping 都上图之后
不管用**——一分钟一个样本，虚线的周期比抖动本身还短，点线和虚线画出来都只是纹理，实际只剩明度
在区分。低彩度配色的替代方案做完并量过，用户决定先不启用。**代码已回滚，这里留下量到的数据。**

**怎么开**：`src/index.css` 加下面两组 `--probe-1..5` 和对应的 `--color-probe-*`，
`NodeDetail.tsx` 里 `PALETTE` 换成这五个变量、去掉 `dash` 字段和三处 `strokeDasharray`。

| | 浅色 | 暗色 |
|---|---|---|
| 石板蓝 | `oklch(0.42 0.075 245)` `#265173` | `oklch(0.56 0.065 245)` `#537998` |
| 赭陶 | `oklch(0.64 0.085 45)` `#b87c60` | `oklch(0.70 0.07 45)` `#c4917a` |
| 鼠尾草 | `oklch(0.50 0.055 175)` `#3f6e61` | `oklch(0.52 0.05 175)` `#497367` |
| 梅紫 | `oklch(0.36 0.06 305)` `#443556` | `oklch(0.64 0.055 305)` `#9484a8` |
| 赭黄 | `oklch(0.58 0.07 85)` `#8d7748` | `oklch(0.60 0.055 85)` `#8f7e5a` |

**量到的四件事：**

1. **彩度 0.055–0.085 是「暗淡」的档位**，约为常规图表配色的三分之一。再高就从「带一点色的灰」
   变成色块，和这个灰阶主题打架。色相取各自最灰的一端；第四条试过 320，出来是糖果品红，305 才对。
2. **对底色的对比度**最低 3.45:1（浅色）/ 3.71:1（暗色），图形元素的门槛是 3:1，够。
3. **去掉虚线后颜色是唯一的区分通道，而它不够。** 赭陶 vs 鼠尾草、石板蓝 vs 梅紫正是红绿色盲会
   合并的两对；明度拉开后这两对彼此的灰度对比是 1.25:1，拉平时 1.03:1，**都达不到能安全区分的
   1.4:1**。约束求解的结论：四种这么暗淡的色相在中性底色上做不到又安静又离得远，调亮或加回虚线
   是仅有的两条出路，都被否了。兜底只能是图例（点一下关掉某条线）。
4. **暗色的明度梯要把浅色那条整段下移，不能向上拉伸。** 为了够到近黑底往上抬，赭陶和梅紫会变成
   粉彩；而区分两条线靠的是**彼此之间**的比值，整段平移不影响——`#cb8e72` 和 `#e6a68a` 是同样的
   1.34:1，但对底色暗一档。

**颜色要量，不要在截图上迭代。** 彩度从 0.09 降到 0.07 在截图上几乎看不出差别；改用 canvas 把
oklch 解析成 sRGB、算 WCAG 相对亮度之后一次定稿。

一周的桶装得下中位数、带和丢包率，技术上没问题。但**一周的探测历史不是这个页面要回答的问题**，
而它现在能回答的那几个窗口里，每一次 ping 都还在图上。

### 每根轴自己声明刻度和顶值 **[用户]**

四个面板，四种错法：

| 面板 | 原来 | 问题 | 现在 |
|---|---|---|---|
| CPU | 写死 `[0, 100]` | 七台里有两台一天都不超过 6%，画出来是贴着地板的直线 | 顶值跟着窗口爬梯，下限 4% |
| 负载 | 和 CPU 共用那根标着 `%` 的轴 | 0.34 画在 0.34% 处，等于不存在 | **整条去掉，见下条** |
| 内存 | `[0, 窗口最大值]` | 457 MB 的机器用 127 MB，线画在面板顶端，读起来是快满了 | `[0, 总量]`，标题写出总量 |
| 硬盘 | 同上 | Alice 用了硬盘的 2.7%，画出来一样贴顶 | `[0, 总量]` |

**顶值由圆整的步长 ×4 倒推，不是反过来。** 直接取圆整顶值的话，底下四条网格线不圆整——75% 的顶画出
18.75 和 56.25,25 000 000 字节的顶写成「23.8 MB」。字节轴的爬梯用 1024 进制，这样步长在它最终打印的
单位里也是圆的。

**刻度全部显式声明，不再猜 recharts。** 它拿到任何 domain 都用自己的十进制 nice-tick:30 MiB 的顶
返回 7.6 / 15.3 / 22.9，和当初把时间轴放在 05:14、10:22 是同一件事。这个组件里每根轴现在都自己说了算。

### `sample_step` 向上取整，否则「预算」不是预算 **[默认]**

原来是 `60 * (hours * 60 / budget).max(1)`。整除向下取整意味着**窗口除不尽时保留更细的 step，
点数就超上限**：`hours=23` 返回 1380 点/序列，对着当时 720 的上限超了 1.9 倍。

而这个上限正是降采样存在的理由——它限的是「任何人都能让 hub 构建的响应有多大」，是资源边界不是
美观。改成 `(hours * 60 + budget - 1) / budget`（`i64::div_ceil` 还没稳定）。

旧断言抓不到：`cap = hours*3600/step + 1` 是从 step 反推的，只证明除法能算，step 让预算被突破时
照样绿。现在直接断言 `SAMPLES + 1`，并把除不尽的 13 和 23 小时加进用例。

**窗口宽度另有上限**，和这条是两件事：降采样限响应行数，`api::PUBLIC_HOURS` 限扫描行数——匿名
168 小时、登录 2160 小时，见 [security.md](security.md)。

### 图表请求带上「这块屏能画几个点」和「要哪一半」 **[默认]**

`/api/nodes/:id/metrics?points=N&series=metrics|ping`，学 Grafana 面板把自己的宽度发给后端。
上限见上面那条分辨率契约（`SAMPLES = 1440`，一天的分钟数）。

**`points` 只往下调，不往上调**：天花板是 hub 的。这条路径不要凭证，谁都能请求，响应有多大不能让调用方定。

**`series` 是全量密度的付款方式**：两个 tab 各画一半却都下载两份，不画的那半占每次响应的 37–62%。
缺省不带 `series` 就是两半都给——curl 和旧主题拿到的还是原来的形状。

### agent 和 hub 之间只守字段，不守版本号 **[默认]**

两个二进制从两个仓库分别发布，而 hub 这边每个读取都以 `unwrap_or(0)` 结尾——agent 改个字段名不会
报错，只会静默记 0，直到有人碰巧去看那张图。这正是铁律 #2 要抓的形状。

做法是每条连接的第一次上报检查 `REPORT_FIELDS`，缺了就 `warn!` 一行。

**否决**：agent 版本下限。它拦不住这个故障——改了字段名的 agent 版本号只会更高，不会更低。
真出现协议断代再加，现在加就是维护一个背后什么都没有的常量。

### schema 版本记在 `PRAGMA user_version` 里 **[默认]**

原来没有版本：每条迁移每次启动都重跑一遍，各自判断「我是不是已经做过了」，而且全部
`let _ = ...` 吞错误——磁盘满和「列已存在」是同一种沉默。

现在 `SCHEMA_VERSION` stamp 进 SQLite 自带的 `user_version`，迁移只在版本落后时跑。
建库时表是空的就直接按当前 schema 建，不走迁移历史。`add_column` 只放过 `duplicate column name`，
别的错误照常往上抛。

**否决**：自己建 `schema_version` 表（SQLite 已经有这个 pragma）、迁移框架（三条迁移）。

### 备份用 `VACUUM INTO`，恢复用在线备份 API **[默认]**

两条都是 SQLite 官方为「热库」准备的路，所以都不需要停 hub、不需要换文件、不需要重启进程。

**导出**：`VACUUM INTO '<临时文件>'` 一条语句拿到一致快照，副本还顺手 compact 过（空页不带出去）。
它写在库文件旁边，`0600`，打开之后立刻 unlink——文件只活在这次响应里，客户端断开也不留残骸。

**导入**：`Connection::restore`（`sqlite3_backup_*`）逐页盖回当前库。**目标文件、权限、journal
模式全都不变**，中途失败整笔回滚，测试里断言恢复后仍然是 `wal`。

**否决**：停服替换文件再重启进程（一键脚本装出来的 hub 由 systemd 拉起，手工跑的没人拉；而且换
文件会把 `0600` 和 `StateDirectory` 的归属一起换掉，还得处理 `-wal`/`-shm` 两个同名残留）；
`ATTACH` + 逐表 `INSERT SELECT`（要为每张表写一遍，schema 一变就漏一张）。

实测（线上库的副本：8 节点、74 023 行 metric、233 386 行 ping_record、7.0 MB）：

| 操作 | 耗时 |
|---|---:|
| `GET /api/db`（含 8 张表的 `COUNT(*)`） | 38 ms |
| 导出 6.7 MB 备份 | 259 ms |
| 恢复 6.7 MB 备份 | 379 ms |
| 删掉 216 008 行探测记录后回收 | 115 ms，7.0 MB → 3.7 MB |

再压到 60 万行 metric、25.8 MB 的库上：导出 975 ms（23.7 MB 文件），导入同一份 966 ms，
回收 886 ms（22.6 MB → 0.1 MB）。

三条都持有 agent 上报用的那把锁，所以都放在 `spawn_blocking` 里跑——这个量级还只是一秒上下，但它
随库线性增长，而其余每条语句都是亚毫秒。导入的校验（`integrity_check` 要读完整个文件）也在里面。

**两个方向都不把文件收进内存**：24 MB 进出各一次之后，进程的 `VmHWM`（历史峰值 RSS）仍是 42 MB，
和启动时一模一样——收下来的字节直接落盘，发出去的直接从文件流走。回收那一次会涨到 61 MB，那是
SQLite 重建 22 MB 库时自己的工作内存，unit 给的是 `MemoryMax=256M`。

`restore` 会拉起两个约束，都在导入前查掉：页大小必须一致（WAL 目标上换页大小返回
`SQLITE_READONLY`），`user_version` 不能比本版本新。低于就跑和重启时同样的迁移——`open()` 和
`restore_from()` 现在共用一个 `migrate(conn, from)`。

### 恢复之后清空全部会话，并给点按钮的人换发一张 **[默认]**

备份里带着它被制作那一刻的 session 行。原样恢复等于让那时还有效、后来登出或过期的会话**复活**，
包括一张被人抄走的 cookie。所以恢复后 `drop_all_sessions()`，然后 `issue_session()` 给当前调用方
——和改密码那条路一模一样的处理，理由也一样：安全动作不该把执行它的人锁在外面。

同时清空 `App.agents`：token 只在握手时校验一次，恢复之后 agent 手里那些可能属于别的节点，甚至
不再存在。让它们断开重连，去对现在这份库。

### 回收空间 = 清过期明细 + `VACUUM` + 截断 WAL **[用户]**

komari 面板上那个「垃圾回收」，这里对着 SQLite 的规范做：`VACUUM` 不能在事务里、连接上不能有活着
的语句、要有与库等量的空闲磁盘、可能重排 rowid。前两条由「一条连接 + 这次调用独占它」保证；第三条
失败也只是回滚，原库不动；第四条对这个 schema 无影响（`metric`、`ping_record` 是 WITHOUT ROWID，
其余表都声明了自己的主键）。

**WAL 模式下 `VACUUM` 之后必须 checkpoint**，否则重建全落在 WAL 里，文件只涨不缩——这是实测到的，
不是照本宣科。`wal_checkpoint(TRUNCATE)` 失败不算失败：空间在库内已经回收了，checkpoint 只是把它
还给文件系统。

先 `prune` 再 `VACUUM`，因为只删行不重建等于把空页留在文件里。保留天数用的就是设置里那个值，
和每小时的巡检同一个口径。

**否决**：`PRAGMA auto_vacuum=INCREMENTAL`（要重建整个库才能改，而且换来的是每次提交都多做一点
搬运）；后台定时自动 VACUUM（一次全量重写，什么时候发生该由人决定）。

### hub 消费主题的**构建产物**，不编译主题源码 **[用户]**

**这条推翻了之前的设计**，推翻的是根，不是枝。

原来 hub 的构建要 clone 主题仓库到 `web-theme/`，装 Node、`npm ci`、`npm run build`，再 embed。
也就是说构建有一个**未声明、可变、无人校验的外部输入**——一个要手工 clone 的目录。它既是「人干活
的地方」又是「构建输入」，两个角色天生冲突，于是静默漂移：那份检出曾经落后 6 个提交还带着未提交
改动，每一次 `cargo build --release` 都成功、无警告地嵌了错的主题。文档里写过警告，没用。

真正的错在于：**默认主题是唯一一个不遵守 hub 自己定义的主题契约的主题。** 第三方主题进 hub 的
形状是一个目录 `{ dist/ + theme.json }`，运行时读，不需要任何工具链；只有默认主题要 hub 把
「编译主题源码」拉进自己的构建里。

现在两者形状一致：

```
主题仓库打 tag  →  CI 构建  →  release 资产 theme.tar.gz + .sha256
                                         │
        hub: web-theme.pin = "<tag> <sha256>"
                                         ↓
        scripts/theme.sh  下载 → 校验 sha256 → 解到 target/theme/
                                         ↓
                            rust-embed 从那里嵌入
```

`theme.tar.gz` 里就是 `dist/` + `theme.json`，**它本身是一个可安装的主题目录**——hub 嵌进去的那个
文件，和用户解到 `<themes>/<short>/` 的那个是同一个，顺带给第三方主题作者留下了范本。

得到的：hub 构建不再需要主题的 Node 工具链、不再 clone、**不再有第二份可能漂移的检出**。sha256
不符构建直接失败（和「不用第三方 action」同一个理由：tag 可以被移动）。

`scripts/theme.sh` 同时被 build.rs 和 CI 调用，一份实现。CI 在宿主机上先跑是因为 release 走 `cross`，
容器里不保证有 `curl`；build.rs 跑是为了本地 `cargo build` 零手工步骤。
stamp 对得上就跳过，所以想拿一个还没发布的主题构建，把它放进 `target/theme/` 再写一行 stamp 即可。

**否决**：把构建好的默认主题 vendored 进 hub 仓库（每次升级约 684 KB 二进制永久留在 git 历史里）；
git submodule（还是一份可编辑的检出，只是漂移变得可见）；只加一个 build.rs 守卫（症状响了，
根源还在——构建输入仍然是人维护的）。

### tailwind 只扫自己的源码 **[默认]**

同一个 tag 构建两次字节不一样：Tailwind v4 默认扫整个仓库，所以 workflow 里新加的
`permissions: contents: write` 就往样式表里塞了一条 `.contents{display:contents}`，连带每个资源
的内容哈希都变了。`api.rs` 里的 `.filter(...)` 同样给后台塞过一条 `.filter`。

两边的 `src/index.css` 都改成 `@import "tailwindcss" source(none)` 加显式 `@source`。各少 1.7 KB，
更要紧的是**产物不再取决于仓库里有什么无关文件**——没有这一条，钉住 sha256 只是把一个不确定的
东西钉住了。

### agent 仓库写死在代码里，不做设置项 **[用户]**

`src/main.rs` 的 `AGENT_REPO` 常量。曾经是 `setting` 表里的 `release_repo`，但没有界面能改它，
唯一会想改的人是 fork 这个项目的人——他们本来就要重新编译。一个从没被写入过的设置行、一次数据库
读取、一段文档，换来的灵活性是零。

顺带的好处：`/agent/{arch}` 转发的 URL 没有一段来自数据库。见 [security.md](security.md)。

## 流量

### hub 侧累加 + boot_id 识别重启 **[用户提的需求，方案是默认]**

需求是 VPS 重启后总流量要能续上，一直累加。

完整机制见 [traffic.md](traffic.md)。核心：agent 报内核 lifetime 计数器 + `boot_id`，hub 只计入
**它亲眼看着计数器涨过去的那部分**；`boot_id` 变了就重新对基线，不计流量。

**否决**：把「当前读数」当增量记进去，无论是读数变小还是 `boot_id` 变了。两种情况下当前读数都可能是
这台机器的整机历史——接口消失（`wg0` 关掉、隧道停了）时是剩余接口的历史累计，`boot_id` 变化时可能
根本是**另一台机器**拿同一个 token 在报。后者实测过：两台机器共用一个 token，会在 `App.agents` 里
互相踢掉再重连，hub 每秒看到两个 boot_id 来回切，每来回一轮总流量涨 180 GB，而 `total` 单调递增、
只能手工校正。

代价是真重启时丢掉「开机到 agent 首次上报」之间的量——systemd/OpenRC 开机拉起、连上就每秒上报，
通常几十秒几百 KB。赌错的代价差几个数量级，所以两边都选重新对基线。

**这条推翻了之前的设计。** 原来 `boot_id` 变化会把当前读数整个计为增量，理由是「计数器刚从 0
开始，当前值就是重启后跑的量」——只看真重启这一个来源时，这个理由成立。

### 总流量和月流量彻底分开 **[用户]**

`traffic` 表里 `total_rx/total_tx`（永不重置）和 `month_rx/month_tx`（按商家重置日重置）是两组
独立的列，同一次上报同时更新。月流量在默认主题里和 CPU、内存、硬盘共用同一个进度条组件（主题仓库
的 `src/components/Meter.tsx`），按节点的 `traffic_mode` 计量——面板的节点表用同一套口径。

### 月度周期按商家重置日算 **[默认]**

`db::period_start()` 处理了短月份（重置日 31 号遇到 2 月落到 28/29 号）和跨年回绕。有专门的测试覆盖这些边界。

**日期取 hub 的本地时区，月和日两条边界都是。** 重置日和「今天」都是人说的日期，得跟人在同一个时区。
原来月边界读 `Utc::now()`、日边界读 `Local::now()`，同一行上的两个计数器对「今天几号」给出不同答案：
CST 的 hub 上，商家月度重置实际发生在重置日当天 08:00，而「今日流量」在 00:00 就翻了。

## 性能

实测数字见 [benchmark.md](benchmark.md)。下面四条是那一轮定下来的取舍。

### WebSocket 每连接读缓冲设成 4 KiB **[默认]**

tungstenite 的默认值是 128 KiB，按大消息传输定的。一个上报包几百字节，200 个 agent 就是 25 MiB 纯浪费的常驻内存。

改动位置：`src/api.rs` 的 `SOCKET_BUFFER`，agent 和浏览器两条 WebSocket 都用它。**要传大消息才需要调回去**，目前两边的帧都远小于 4 KiB。

### 节点列表一次查完流量，不逐个查 **[默认]**

`node_view()` 原来自己去查一次 `traffic` 表并拿一次实时状态的读锁，渲染 200 个节点就是 200 次查询、200 次加锁，全部排在 agent 的写入前面。现在 `visible_nodes()` 一次 `all_traffic()` + 一次锁，把结果传进去。

**所以 `node_view()` 不再拿 `&App`。** 加新字段时它需要什么就从参数传进去，别在里面重新查库。

### `/api/nodes` 复用 WebSocket 的快照缓存 **[默认]**

`live_snapshot()` 的 2 秒缓存本来只有浏览器的 WebSocket 流在用，HTTP 那条路每次请求都重新渲染一遍全量 JSON。公开状态页被人转发一次就会把这条路打满。

代价是缓存的帧里多了一个 `admin` 字段（两个消费端都只读 `nodes`，忽略多余字段），以及 HTTP 拿到的数据最多旧 2 秒——和 WebSocket 流本来就一样。**任何改节点的写路径都必须调 `invalidate_snapshot()`**，否则面板改完刷新看到的还是旧的。

### 桶在 Rust 里折，不在 SQL 里排 **[默认]**

延迟图要的是每个桶的中位数、极差和丢包率。原来整段交给 SQLite：两个窗口函数按
`(task_id, ts/step, latency>=0)` 分区排名，外面再 `GROUP BY` 一次。**三次全窗口排序，换一次索引 seek。**

`ping_record` 的主键是 `(node_id, ts, task_id)`，所以按时间窗读出来的行**本来就是时间序**——
下一个桶开始，上一个桶就齐了。于是只读原始行，在 Rust 里边读边折，同时手里只有一个桶。

实测（线上库 8 节点 4 个探测、7 天保留、`node 1` 有 29 760 行，21 次请求取中位数）：

| 窗口 | 窗口函数 | Rust 折叠 | |
|---|---:|---:|---|
| `hours=1` | 4.7 ms | **2.8 ms** | 1.7× |
| `hours=6`（主题默认） | 26.2 ms | **9.3 ms** | 2.8× |
| `hours=24`（延迟 tab 上限） | 61.7 ms | **16.5 ms** | 3.7× |
| `hours=168`（匿名上限） | 284.0 ms | **54.1 ms** | 5.2× |

抖动也一起没了：`hours=168` 原来最快 154 ms、中位 284 ms，现在是 46 ms 和 54 ms——排序会不会
溢出到临时文件，取决于那一刻的缓存。这条路**匿名可达**，代价落在 agent 上报用的那条唯一的写连接上。

改完对着线上库的 123 小时全量数据，8 个节点逐个比对新旧二进制的响应：**逐字节相同**。

**中位数的定义没变**：奇数取中间那个，偶数取中间两个的均值向零取整，超时（-1）不进中位数只进丢包率。
`api.rs` 的 `a_thinned_bucket_answers_with_its_mean_and_says_what_it_lost` 把奇数、偶数、全超时、
一桶 180 个丢 1 个都写死在里面了。

**`ORDER BY ts` 是写给人看的**：主键已经保证了这个顺序，加上它计划里也不会多一个 sorter，但
折叠依赖这个顺序，所以让它出现在 SQL 里，而不是靠读代码的人自己去推主键。

### 调过的 SQLite 参数只有三个 **[默认]**

默认值里不合适的就这几条：`cache_size = -8192`（8 MiB page cache，几百个节点的工作集装得下，读路径不再回落到文件系统）、`wal_autocheckpoint = 256` 和 `journal_size_limit = 1 MiB`（否则 WAL 会涨到最忙那一分钟的大小再也不还回去，而 hub 是小机器上的长驻进程）。WAL、`synchronous = NORMAL`、`busy_timeout` 用的是默认或惯例值。

**考虑过没做的三条**：`_txlock=immediate`（这里只有一个连接、外面一把 Mutex，不存在锁升级冲突）、上报批处理（`metric` 表每节点每分钟才写一行，本来就没有可批的量）、`temp_store = MEMORY`（实测**更慢**：`metric` 那个 GROUP BY 从 12–13 ms 变成 14–17 ms，两轮都是。编译进来的 `SQLITE_TEMP_STORE=1` 本来就不落盘，这条 PRAGMA 只是换了一套分配路径）。

PRAGMA 是**每连接**的，用 `sqlite3` 命令行去读只会读到它自己那条连接的默认值。`db.rs` 里有个测试守着这几个值真的落到了 hub 用的那条连接上。

## 安全

### GitHub SSO + 本地应急密码 **[用户]**

GitHub 挂了、OAuth App 配错了、被墙了，纯 SSO 会把人彻底锁在自己的后台外面。细节见
[security.md](security.md)。

### 公开状态页默认开启 **[用户]**

可以在设置里全局关，也可以按节点关（`node.public`）。

**公开视图永远不输出 `ip`、`hostname`、`remark`**——`src/api.rs` 的 `node_view()` 里 `full=false`
时这三个字段根本不写进 JSON。有测试守着。

### 手写 OAuth，不用 oauth2 crate **[默认]**

GitHub OAuth 就是两个 HTTP 请求。`oauth2` crate 带一堆用不上的 flow 和类型体操。手写约 40 行，state nonce 用 HttpOnly cookie 防 CSRF。

### 节点 token 明文存库，管理员密码用 argon2 **[用户]**

节点 token 存在 `node.token` 里，不做哈希，**为的是面板能随时重新显示安装命令**——见「安装命令
随时可看」。

代价是能读到数据库的人可以冒充节点上报假数据。接受它的理由是数据库里还有 session、GitHub client
secret、argon2 哈希，本来就必须当机密对待；节点 token 不比它们更敏感，换来的是一个每天都要用的
功能。管理员密码是人选的低熵值，仍然必须 argon2id；session token 仍然只存 sha256。

**否决**：可逆加密（密钥还得存在同一个数据库旁边，只是把问题挪了个位置）。

### release 用 runner 自带的 gh，不用第三方 action **[默认]**

发布这一步拿着 `contents: write`，是整个 workflow 权限最高的地方。用 `softprops/action-gh-release`
等于把这个 token 交给一个第三方仓库的 tag，而 tag 是可以被移动的。runner 本来就装了 `gh`，
`gh release create ... --generate-notes` 一行做同样的事，少一个供应链入口。

同理，tag 守卫放在发布那一步而不是整个 job 上：`workflow_dispatch` 能完整跑一遍构建和产物收集，
不会真的发出版本，改完 workflow 不用靠打 tag 来验证。

**否决**：把第三方 action 钉到 commit SHA（能防 tag 被移动，但每次升级都要手动换 40 位哈希，
而这里根本不需要这个 action）。

## 前端

### 公开主题独立仓库，后台留在 hub **[用户]**

主题只拥有公开状态页；登录页与 `/admin/*` 固定在 hub。真正的换主题能力来自 hub 运行时读取
`<themes>/<short>/dist`，不是拆仓库本身：选中的主题缺失、损坏或被删除时自动回落内置默认主题，
零配置启动和恢复入口因此始终可用。

默认主题放在独立的 `monitor-theme-default` 仓库，发布 `theme.tar.gz`，hub 按 `web-theme.pin`
下载校验后作为内置 fallback 嵌入（机制见「hub 消费主题的**构建产物**」）。代价是一个明确接受的
跨仓库构建依赖，换来独立的主题版本、契约和开发流程。

**否决**：让主题接管后台（每个主题作者都会被迫实现节点 CRUD、OAuth、密码修改）；zip 上传（需要
额外依赖并扩大 zip-slip 攻击面，复制目录 + 面板选择已经够用）。

### shadcn/ui **[用户]**

`web-admin/src/components/ui/` 和主题的 `src/components/ui/` 是 CLI 生成的组件，**不要手改**——
要改样式改各自 `src/index.css` 里的 CSS 变量。用不到的组件已删（dropdown-menu / progress /
tooltip / sonner 的 wrapper）。

### 节点接入分两步 **[用户]**

首次添加只填名称，不打断配置。需要部署时再点节点旁的下载按钮，调整 agent 支持且实际有用的参数：
上报间隔（默认 1 秒），以及仅用于下载 GitHub Release 的代理。

节点的展示/流量设置留在普通编辑里，价格、付款周期、到期日放在独立的「续费设置」里。

**额外排除的网卡前缀已经删掉** **[用户]**：agent 内置的虚拟网卡前缀列表够用，多一个输入框、多一条
install.sh 分支、多一路 agent 参数，只为一个没人填的框。hub、install.sh、agent 三边一起删。

### hub 自己转发 agent 二进制 **[用户]**

`install.sh` 默认从 `<hub>/agent/<arch>` 下载，hub 去 GitHub Release 取回来再转发。起因是一台
IPv6-only 的 Alpine 机器：github.com 没有 AAAA 记录，试过的三个加速站里只有一个能用（还要 10 秒），
而它访问 hub 只要 0.6 秒。节点本来就得连上 hub 才有意义，就让 hub 顺手把二进制递过去。

并发转发数由 `main::RELAY_GATE` 限到 4——这条路匿名可达，一次请求转出 1.8 MB。

**GitHub 代理是 hub 的设置，不是安装命令的参数** **[用户]**：退路本身要留（hub 拉不到 release 时，
`/agent/<arch>` 整条路都是 502，所有节点都装不上），但它原来是面板安装弹窗里的一个输入框，per-install
且不持久化——hub 连不上 GitHub 对**所有**节点都成立，却要每加一个节点重填一遍同样的地址。搬进
「设置 → 站点」填一次，由 `main::release_url` 在 hub 侧拼上，节点侧回到「只连 hub」这一个前提。

一并删掉的：`install.sh` 的 `--github-proxy` 参数与那一路 URL 分支、面板的输入框和 `shellArg()`、
`install.sh` 里的 `@@REPO@@` 占位（连同 `install_script()` 的替换——脚本不再需要知道仓库名）。
代价：手上存着旧安装命令的人会撞到 `unknown option: --github-proxy`，重新生成即可。

**否决**：hub 侧缓存二进制（安装是低频操作）、把二进制打进 hub（每次发 agent 都要重发 hub）。

### install.sh 支持 OpenRC **[用户]**

agent 本来就是 musl 静态二进制，Alpine 上跑得了，缺的只是 init 脚本。systemd 那套加固
（`DynamicUser`、`ProtectSystem`）在 OpenRC 下没有对应物，用 `supervise-daemon` 拿到等价的自动重启。

### 重复执行安装命令是幂等的 **[默认]**

同一台机器上再跑一遍安装命令**不会起第二个 agent**：服务名固定是 `monitor-agent`，二进制、env
文件、unit 文件全部整份覆盖，最后 `systemctl restart`（不是 `enable --now`，那个会放过已经在跑的
服务）。实测连装三次，始终是一个单元、一个进程，跑的是最后一次的参数。

**下载成功之后、覆盖二进制之前先 stop 一次**。unit 每次都重写，所以不需要完整卸载再装。stop 换来
两件事：不必依赖 `install` 恰好会 unlink 而不是撞上 `ETXTBSY`（换成 `cp` 就会失败），以及消掉
「新二进制已落盘、旧进程还在跑旧代码」的那段窗口。

放在下载**之后**：拉不到二进制的节点保持原样继续跑，而不是先被停掉再发现装不上。

### 面板可以手改流量计数 **[用户]**

`PUT /api/nodes/{id}/traffic` 一直都在，只是没有入口。节点换了机器，boot_id 变化会让 hub 把新机器的
历史计数当成一次增量记进来（见 [traffic.md](traffic.md)），编辑弹窗里的「流量校正」就是给这种情况准备的。
按 GiB 填写；没动过输入框就不发这个请求，免得四舍五入把几百 KB 抹成 0。

### 到期日自动顺延 **[用户]**

过期当天还在上报的节点显然是续过费了，只是没人回来改日期。hub 每小时巡检一次：节点在线、到期日
已过、付款周期不是「一次性」，就按周期整月往后推，一直推到今天之后（`src/main.rs` 的 `renewed()`）。
月末日期由 chrono 的 `checked_add_months` 收敛到下月最后一天，1 月 31 日续成 2 月 28 日。

只动日期，不碰钱：不做自动扣款，也不给离线节点顺延——节点掉线才是真到期的信号。

**否决**：每个节点一个开关（还没人需要按节点关掉）、到期通知（通知已被砍掉）。

### 安装命令随时可看 **[用户]**

**这条推翻了之前的设计。** 原来只存 token 的哈希，面板没法把命令显示第二遍——每次打开安装弹窗都
得换发一个新 token 才能拼出命令。

那个设计错得很隐蔽：`InstallDialog` 一挂载就 `POST /nodes/{id}/token`，所以**光是点开那个图标，
凭证就已经换掉了**，不需要复制、更不需要粘到机器上执行。当时 hub 又不会断开已连上的 agent，于是
节点看起来一切正常，直到它下次重连——hub 重启、网络抖动、VPS 重启——才永久 401，而中间隔了多久
无从倒推。生产环境掉过一个节点。

现在 token 明文存库，随节点列表下发给面板，安装命令在前端本地拼出来，**打开弹窗一个请求都不发**。

`POST /nodes/{id}/token` 保留，但只作为显式的「换发凭证」按钮，带二次确认，用于怀疑凭证泄露时。
换发会立刻断开那条连接（`api::reset_token` 把这个节点从 `App.agents` 里删掉）：token 只在
握手时校验一次，光改库里的值不会打扰已经连上的 agent。

拼命令用的地址是 `me.site || location.origin`：给了 `--site` 就用它，没给就用浏览器地址栏。前者
覆盖的是「面板的地址不等于节点该用的地址」（监听回环再走隧道进后台），后者让常规反代零配置——换个
域名进后台，命令自己就跟着变。

### recharts **[用户]**

打包后 774 kB（gzip 232 kB），大头是它。在保留 / 换 uPlot / 自己写 SVG 之间选了保留：主流选择，
且项目原则是不自己造轮子。带 hash 的资源设了 immutable 缓存头，只加载一次。

它只进详情页的分包，落地页不加载——见主题仓库 `src/App.tsx` 的 `lazy` 分割。

### 后台六个路由，「安全」从「设置」里拆出来 **[用户]**

节点、延迟、数据、主题、安全、设置。原来 GitHub 单点登录和应急密码是「设置」页最下面的两张卡片，
和站点名称、保留天数排在一起——**进后台的两条通道，和一个改站点名的输入框同一个层级**。拆出来之后
「设置」只剩站点那一张卡，「安全」页上只有登录相关的东西。

「数据」是新的一页：数据库大小、WAL 大小、可回收字节、各表行数，加上导出备份、导入备份、回收空间
三个按钮。**只放这些**——库里还有一堆能查的数字（页大小、schema 版本、最早一行的时间），但那些
回答不了「我这个库现在多大、能不能瘦一点」以外的问题。

「延迟监控」顺手改叫「延迟」：六个标签并排时，只有它是两个词。

### 不用 react-router **[默认]**

后台只有几个内部页面。`web-admin/src/App.tsx` 里的小型 `usePath()` 就够了，用 `history.pushState` + `popstate`。
